# Serverless My Devices

Design baseline: main `274dbeb`, including the existing working-tree changes inspected for this proposal. This is an implementation plan, not implemented behavior. “Account” means a portable cryptographic identity; no email, password login, account directory, or hosted recovery service.

## Existing constraints and integration points

- `iroh_net.rs::load_or_create_secret` persists a 32-byte ed25519 seed in `iroh-identity.key`; its public key is the device's `EndpointId`. Keep each installation's key unique and stable.
- `models.rs::Friend` has a local UUID `id`, one `endpoint_id`, name/`name_custom`, avatar path, `auto_accept`, legacy secret/role, and endpoint-specific `progress_v`. `friends.json` is atomically backed up; `friends::reconcile` merges endpoints and some unkeyed name matches, migrating chat threads.
- `friends.rs::my_code` emits `dropbeam:` + base64url JSON `{v:1,eid,name}`. It is public and reusable, with no secret. The current decoder does not enforce `v`. `dropbeamf1:` separately carries an invite ID, shared secret, name, and optional endpoint.
- `friend-hello` authenticates the connection via `conn.remote_id()`, exchanges profile data, and can auto-add the reverse friend. `apply_hello` can rebind a claimed friend ID; that behavior must never authorize a group join or overwrite an already pinned endpoint.
- `iroh_net.rs` multiplexes framed JSON streams on `dropbeam/1`; `friend_conns` caches outgoing chat connections. Its connection monitor refreshes presence every 45s only on new received datagrams. Folder control beacons carry rosters, roles, pause state, and deletes; larger reconciles use separate streams.
- `src/lib/presence.ts` currently combines name-keyed timestamps and folder names with a 120s window. This cannot distinguish two people with the same name or safely aggregate devices.
- `chat.rs` stores threads by friend UUID in `chats.json`, retains 2,000 messages/thread, and has logical ordering, edits/deletion tombstones/reactions plus `chat_ops.json`. Despite stale introductory comments, `spawn_chat_outbox_retry` retries queued messages/ops with backoff. Missing ACKs currently can return success; persistence failures are logged rather than propagated.
- `Pair`/`pairs.json` remain endpoint relationships: local path, pair secret/role, `endpoint_id`, folder `group_id`, `owner_eid`, and role/pause epochs. `pairing::ensure_member` derives links from folder group + two endpoints. `sync.rs::reconcile_friends` currently emits updates without starting legacy inbox workers.
- The transport already uses n0 discovery/relays, optional custom iroh relay, mDNS, and `peer-addrs.json`. Serverless identity requires no new central service; it does not mean internet rendezvous works without reachable discovery/address hints or relay infrastructure.

## Identity and authority

1. On “Create My Devices”, generate an independent ed25519 root key `R0`. Define `account_id = "acct:" + base32(SHA256("dropbeam-account-v1" || R0.public))`. Use `account_id` in code/storage to avoid confusing it with folder `Pair.group_id`.
2. The first device is the **management device**. Only it holds the root private key, encrypted through an OS keystore-backed secret store; linked phones/tablets receive public authority and memberships, never that private key or another device's endpoint seed. Adding/removing devices requires this device or explicit recovery. This deliberate single-writer authority avoids concurrent membership administration.
3. A root-signed membership is `{v,account_id,root_generation,serial,endpoint_id,rights:["account-sync","contact"],issued_revision}`. Endpoint possession is proven by QUIC and a signed enrollment transcript. A certificate alone grants nothing to a different `conn.remote_id()`.
4. A root-signed full roster is `{account_id,root_generation,revision,prev_hash,active_cert_hashes,revoked_serials}`. Keep the signature chain and highest accepted revision/hash on disk. Removal changes the authoritative roster, not an LWW setting. Same-version divergent hashes are an authority fork: freeze membership changes and require recovery, never choose by timestamp.
5. Sign canonical CBOR bytes with distinct domain prefixes for membership, roster, rotation, endpoint hints, link transcripts, and sync operations; JSON wire envelopes carry the signed bytes. Verify bounds, schema, signatures, account hash, chain continuity, and active membership before applying state. Reuse vetted ed25519 implementations; do not invent signature encodings.
6. Root signatures authorize identity membership only. Ordinary member keys sign profiles, sync operations, and their own expiring address advertisements. Names, platform labels, IPs, and avatars are display/routing metadata and never merge criteria or authority.
7. `DeviceRecord` separates endpoint identity/certificate from mutable label, capabilities, signed address hints, and locally observed last-seen. Cap v1 at 16 active devices; paginate historical roster changes. Store address hints with signer sequence and 24h expiry; accept connections only to the certified endpoint regardless of hints.
8. All members can read/write the replicated personal dataset: linking grants access to contacts/settings and, in Phase 3, retained chats. This is a trust boundary, not a limited file-transfer pairing. It grants neither root administration nor Lab Mode nor automatic access to shared folders.

### Public friend codes and compatibility

- Emit `dropbeam:` + base64url JSON `{v:2,eid,name,account:{id,genesis_key,root_chain,roster,members},endpoints:[{eid,hints,expires,signature}]}`. Include the presenting device and currently advertised member endpoints; `eid` remains that presenting device for v1 decoders. No enrollment token, root seed, pair secret, or private address book belongs in a public code.
- Bound decoded codes at 32 KiB; use a QR-size compact form with genesis, presenting membership, signed roster commitment, and one endpoint. Fetch the remaining signed roster/chain over that pinned endpoint before accepting group identity. A partial code may establish a legacy device contact but cannot authorize unseen members.
- Public codes allow anyone holding one to attempt contact, as today; they cannot enroll themselves. Code authenticity is trust-on-first-use from the user's chosen sharing channel, not proof of a real-world name. A certificate signed by an attacker's own root does not establish someone else's identity.
- New parsers accept existing `dropbeam:` v1 and `dropbeamf1:` unchanged as endpoint/legacy contacts; reject unsupported versions explicitly. Old parsers ignore v2 extras and add only `eid`. Provide “Copy code for older version” using v1. Keep old folder invite `dropbeam1:` entirely separate.
- Advertise `account_v:1`, `device_sync_v:1`, and later `chat_sync_v:1` in hello **requests and replies**, independently of `progress_v`. Only send new stream kinds after negotiation; no global ALPN bump is needed. Absence means legacy; invalid account proofs mean rejection, never silent downgrade of a known account.
- Upgrade an existing endpoint contact only after that same authenticated endpoint presents a valid active membership and signs a challenge binding its endpoint to the account. Merge other records only on matching verified account IDs; never on names or sender-supplied friend UUIDs. An endpoint already pinned to another account needs explicit identity-change acceptance.
- Keep old endpoint bindings/UUID redirects so existing chat IDs and in-flight transfers resolve. Upgraded friends learn the roster on hello/reconnect and can reach any known member. Old peers still see devices separately: default to a designated compatibility endpoint and explain that continuity requires the friend's upgrade. Do not promise a transparent legacy solution.
- An old public code stays useful while one advertised endpoint is reachable and can supply updates. If every endpoint in it is retired, there is no serverless lookup by account ID alone: share a fresh code. An online home device can bridge roster gossip; the optional relay is not an account directory or mailbox.

## Secure linking flow

1. On management device A, select “Link a device”. Show `dropbeamd1:` + base64url `{v,account_id,root_fingerprint,inviter_eid,address_hints,session_id,token,expires_at}`. Generate a random 256-bit token and session ID; authorize for 5 minutes using A's monotonic deadline. Keep the token out of logs/URLs/history; store only its hash with pending state. Restart invalidates unfinished invitations.
2. B scans A's screen or pastes the code. B keeps its existing endpoint seed, dials the pinned A endpoint, and sends `device-link-request` with session ID, token, B endpoint, nonce, proposed label, and B's signature. A checks expiry, token hash, matching remote endpoint, rate limits, and proof of possession before displaying a pending request. No contacts or secrets are returned yet.
3. A returns its nonce, public authority chain, and endpoint-signed challenge; B checks the root fingerprint against the code and signs the completed transcript. Both display a short authentication string derived from that domain-separated transcript: account/root fingerprint, both endpoints, session ID, both nonces, and token hash. Use at least 40 bits rendered as words, bound to this exact candidate. A requires local unlock and explicit “Link this device”; B explicitly confirms joining the shown identity.
4. In-person QR: scan directly from A, compare the words on the two physical screens, approve both. A photograph or clipboard copy of the QR gives the attacker a chance to request enrollment or cause nuisance, not automatic membership. Names supplied by a requester must never replace the word comparison.
5. Remote paste: compare words through an independent authenticated channel (e.g. an already trusted call), not just the same potentially compromised chat carrying the code. If that comparison is unavailable, cancel linking. A thief with the code can race B or impersonate its label; tricking the owner into approving the thief's matching transcript would grant full member access. One-time use alone does not stop this race.
6. Reserve only the candidate the owner approves. Persist the consumed session ID bound to B plus the new signed membership/roster atomically **before** returning them. B verifies and durably installs them, ACKs, then starts sync. Retries by that same B are idempotent and retrieve the committed result; replay by any other endpoint fails. A lost final ACK shows “Linked; sync pending”, not a new invitation.
7. Cancellation/expiry before commit invalidates the token; after commit use device removal. Bound unauthenticated attempts, frame sizes, concurrent requests, and UI prompts. Neither `friend-hello`, a folder invite, nor possession of a public friend code can enter the enrollment handler's commit path.
8. All existing members receive the new root-signed roster and derive own-device contacts automatically. Use a separate `own_devices` view/projection, excluding self and ordinary Friends counts; own-device sends can auto-accept without manual friend-adding. Avoid copying legacy inbox secrets or deriving secrets from public account IDs.
9. An existing standalone B previews an import before joining: union its contacts, adopt A's account profile/settings by default, and offer explicit selection of B's aliases/settings to import as new operations. Installation defaults must not win over established account preferences. Do not silently merge two established accounts. Joining another account requires an explicit leave/identity-change flow; B's old endpoint contacts can need re-verification, and its folders/history remain local until separately migrated.

## Personal-state replication

### Dataset boundaries

| Replicate between active own devices | Keep local |
| --- | --- |
| Verified external account/endpoint contacts, explicit additions/removals, owner aliases (`name_custom`), profile names | Local friend UUID bindings, legacy roles/secrets, endpoint progress capabilities, connection caches/presence |
| Own profile avatar and cached friend avatars by content hash; profile ownership separate from local alias | Absolute avatar paths, OS photo permissions; resolve each blob hash to a local cache path |
| Allowlist: `display_name`, `theme`, `show_megabits`, `send_read_receipts` | Download/folder paths, launch/tray settings, notifications/sounds, bandwidth/direct/relay settings and passwords, Giphy key, recovery budgets |
| Phase 3: retained messages, mutations, delivery/read facts | Phase 1–2 history; attachment bytes/paths, file-transfer execution state and recovery history |
| Public root/membership/roster chains | Endpoint/root private keys, `diag-id`, diagnostics URL/consent/logging, Lab Mode/operator grants |

- `auto_accept` stays device-local: imported external contacts default to manual accept; existing local choices survive. Own-device auto-accept is a separate membership-based policy. Remote profile changes never overwrite an owner alias; resetting an alias is a replicated explicit operation.
- Sync only avatar bytes whose hash matches the record; validate image type/dimensions, strip metadata, cap at 256 KiB. Do not replicate arbitrary paths or fetch arbitrary remote URLs. Profile changes flow outward through hello only after local persistence.
- Friends' public roster proofs may be copied inside the account; a signed proof permits group recognition. A copied endpoint-only contact does not make a legacy friend trust B. Phase 1 does not broadcast unsolicited hellos from every sibling to imported external contacts; selecting one for a send can introduce B with the existing device semantics.

### Protocol, ordering, and catch-up

- New `account-sync-{hello,summary,request,ops,ack,snapshot}` streams reuse the framed `dropbeam/1` connection infrastructure, not folder control messages. Generalize the outgoing connection helper; open bidirectional streams on incoming connections only when negotiated. At most one sync session per endpoint, coalesced retries with jitter (12s→60s→300s), wake on local edits/roster changes/reconnect.
- First exchange and verify roster chains. Every stream requires `conn.remote_id()` to be an active member of **our** account. A friend from another account may exchange only its public membership/profile data; it cannot request our personal snapshot. Recheck authorization per batch and close streams immediately on observed revocation.
- Each durable operation is `{schema,account_id,author_eid,author_counter,lamport,record_type,record_key,field,value_or_tombstone,context,signature}`. Counters are persistent per author; operation ID is `(author_eid,author_counter)`. Validate authors against membership and reject counter reuse with different bytes. Signed operations allow B to relay C's updates while C sleeps.
- Profiles/settings/aliases use per-field LWW registers ordered by `(lamport,author_eid,author_counter)`. Increment `max(local,received)+1`; wall clocks affect display only. Losing concurrent values may be retained for diagnostics locally, never uploaded. Incoming contact sets are unions of operations, not replacement `friends.json` files.
- Contacts use remove-wins generations: a removal tombstones the current generation and beats edits/concurrent re-adds. Explicit “Add again” must reference all observed removal IDs and creates a new generation; an unseen concurrent removal still wins. Keep compact deletion contexts indefinitely so a long-offline device cannot resurrect a deleted friend.
- Apply tombstone checks to hello, folder-derived upserts, and chat identity resolution too. An existing folder may remain shared after removing its friend contact; its beacon must not silently recreate that contact. Folder trust does not grant personal-state sync.
- Exchange per-author contiguous counters plus missing ranges; ACK only committed contiguous ranges, never a maximum that skips holes. Transfer bounded batches (≤128 operations and ≤64 KiB encoded, below the existing 1 MiB frame cap), with flow control and bounded concurrent blob streams so account sync cannot starve transfers.
- Use an append-only local operation journal and atomic checkpoints with checksums, state, causal/deletion metadata, signed winning records, and per-author watermarks. ACK after durable write; apply the journal into UI/storage projections before emitting events. Crash replay is idempotent; failed writes leave the sender's outbox pending.
- Keep a 30-day/32 MiB delta window, compacting only after a durable checkpoint. A device behind the retained floor exchanges validated snapshots **and merges its own pending operations**, then resumes deltas. Snapshots never overwrite local unacknowledged edits, accept lower roster revisions, or erase tombstones. Membership history remains available independently of journal compaction.
- Catch-up can use any active sibling carrying the data; no quorum or always-online coordinator is needed for personal records. Updates propagate only across overlapping online sessions. If all copies of an unsynced update are lost, it cannot be recovered; an optional always-on own device improves availability but the relay stores nothing.
- Membership authorization is stricter than data ordering: once revocation is known, reject newly arriving raw operations from that removed author, even if they claim an earlier clock. Already committed historical records remain. A current active sibling may sign a snapshot attesting to its committed historical state for new-device catch-up; this trusts that sibling as a dataset writer, not the revoked signature. Absence of trusted timestamps prevents distinguishing withheld legitimate edits from post-theft writes.

### Storage and migrations

- Add `account.json` (schema, genesis/current root chain, roster, local membership, keystore reference), `account-sync/` (journal/checkpoint/blobs), and `contacts-v2.json` (canonical contacts plus legacy redirects). Private roots never enter these JSON files or generic app backup/export paths.
- Canonical contact key is `acct:<hash>` for verified groups, `dev:<eid>` for endpoint-only contacts, or `legacy:<origin-eid>:<friend-uuid>` when unkeyed. Keep a durable local-UUID→canonical-key map; do not export another device's UUID as global identity. Own-device entries are derived from the roster, not independently editable contacts.
- Initially project contacts to additive `Friend` fields (`contact_key`, optional `account_id`, `device_ids`, `is_own_device`); preserve legacy fields/IDs. Move per-device address, capability and receipt state out of the single Friend endpoint slot in Phase 2. Keep `Pair.group_id` and all pair IDs unchanged.
- Run migrations before networking/UI startup under one storage writer. Create backups, stage outputs, write a migration manifest, atomically switch schema marker, and resume/roll forward idempotently after a crash. Read/parse failures must stop migration without generating empty replacements; retain the existing anti-clobber guards.
- Phase 2 rewrites `chats.json`, `chat_ops.json`, and `detached-chats.json` references through the verified alias map in one recoverable migration. Union messages without losing sender/direction distinctions; preserve queued operations and `file_xfer_id`. Phase 3 imports device-local paths into a separate attachment-location table. Unknown/unkeyed identities stay distinct until proven.
- Older binaries cannot preserve the new journal or revocation rules: rollback means restoring a pre-migration backup and explicitly relinking afterward, not concurrently editing the new account through old and new binaries. Never feed additive compatibility projections back as authoritative account snapshots.

## What friends see and where sends go

- Phase 2 presents one row/thread per verified `account_id`. An authenticated active device may introduce the account's signed roster; accepting the account trusts its root to add future devices. Roster gossip goes to already connected contacts on changes and reconnect, with public proofs only. Do not share our friend list with friends.
- Presence is locally measured per endpoint, aggregated by canonical contact ID: online if any nonrevoked member has traffic within 120s; otherwise offline if previously observed, unknown if never observed. Never use names, relayed last-seen claims, or mere membership as liveness. Folder events map `pair_id → endpoint → contact` explicitly.
- Keep lightweight negotiated hello/keepalive sessions to known devices (45s traffic observation, bounded dialing/backoff). Reuse live connections; do not start a second polling loop per UI view. Show per-device availability in a contact detail view; OS-suspended phones count unavailable until reachable again. No serverless background-push guarantee is implied.
- Default chat policy: send to **one** eligible online device, preferring a live connection, then a recent successful endpoint, then deterministic endpoint order. Dial other known members on failure. A durable ACK from one recipient means “delivered”; absence of a valid ACK stays queued. Read means a recipient device actually displayed the message, not that all devices did.
- Assign one stable logical message ID before the first attempt, retain it on failover, and include sender account/device and signed payload. Minimal Phase 2 per-message receipt/dedup metadata gossips between own devices; a partition can still produce duplicate physical deliveries/notifications. Claim at-least-once delivery with eventual deduplication, never exactly-once behavior across disconnected recipients.
- Phase 2 history remains local to the sending/receiving device, with a clear “History on this device” label. One contact and multi-device routing do not by themselves synchronize conversation content; Phase 3 completes that experience. Offline messages stay in the originating sender's durable outbox until Phase 3 can replicate them.
- File send policy: choose one device, show its label, and allow an explicit device picker. Once that device accepts, pin transfer/resume and destination to it; never fan out file bytes or automatically fail over after acceptance/ambiguous completion. Manual retry to another device warns of a possible second copy. Transfer progress and file paths stay device-local.
- A linked device can send directly to another own device through the same file channel without a friend code. Receiving files from friends still obeys that destination device's `auto_accept` setting. Sending to all own devices is an explicit future action, not the default.

## Shared folders stay per device

- Linking an iPad must not start mirroring Mac directories. Do not replicate `pairs.json`, filesystem paths, pair secrets, mirror/delete settings, pending deletes, or watcher state. Offer read-only “Shared on Mac” metadata only as a later optional feature; it is not a local mount.
- “Use this folder on this device” requires a local folder choice and explicit folder invitation through `pairing.rs`. Existing folder owner/endpoint roles apply; account membership never upgrades a viewer or grants a sibling a folder seat. Preserve per-device `owner_eid`, `role_epoch`, and `pause_epoch` behavior.
- Folder membership/presence can display one person with nested device seats while retaining separate endpoint links. Never substitute an arbitrary online sibling into `send_folder_ctrl`, `send_folder_file`, roster construction, or pair-ID derivation. Audit those authorization gates when adding the account resolver.
- Revoking an own device also stops local folder connections to its endpoint. Notify reachable folder owners/peers with the signed revocation, but removing that seat/reissuing invitations remains a separate folder action. Account revocation cannot erase already copied folder data or retroactively secure legacy folder secrets; compromised shares require new secrets/links and owner-driven roster updates.

## Phase 3: conversation convergence

- Replicate message events and mutation events, not whole thread replacements. Identity is `(sender_account_or_legacy_endpoint,author_eid,message_id)`; retries preserve it. Conversation key is the other canonical contact (global event context includes both parties). Derive `from_me` from the verified historical author/account binding, preserving it after revocation; never copy its source-device boolean blindly.
- New group-capable messages/edits/deletes/reactions have author signatures bound to both conversation parties and target event. Siblings forward those bytes; legacy messages become signed import attestations by the receiving own device and cannot establish new external authority. Only the author's account may edit/unsend its messages; reaction ownership is by reactor account.
- Merge immutable originals by event ID; resolve edits by the register ordering above, deletion tombstones dominate all edits, and reactions are LWW add/remove per `(target,reactor_account,emoji)`. Retain bounded pending mutations for missing targets and request those targets; apply unsend tombstones even before the original arrives.
- Preserve the original logical clock on replication; order by `(lamport,author_eid,message_id)`. Legacy imports use a stable origin-endpoint/direction/old-ID mapping and existing `seq/ts` as migration ordering metadata. Do not regenerate IDs/clocks at every receiver or conflate unrelated legacy messages with equal IDs.
- Delivery/read facts are monotonic sets of message IDs (batched ranges per author), not wall-clock “read up to”. Read on any own device clears corresponding unread entries on siblings; emit external receipts only when the synchronized privacy setting allows it. Delivery/read cannot regress because a sibling retries and fails. Typing remains ephemeral.
- Replicate outgoing messages before/alongside delivery; any sibling with an original may retry with the same signed ID. Prefer the originating device while reachable, but rely on receiver deduplication rather than distributed locks. Legacy peers lack group-wide deduplication: only the originating device sends/retries to them; siblings display replicated history without taking over delivery.
- Make `chat.rs` writes return errors and require a persisted message/op plus dedup record before an ACK or delivered UI state. ACKs carry the logical message ID and authenticated recipient endpoint. A timeout/connection close is not proof of durable receipt. Duplicate events must not create new unread counts or file-transfer bubbles.
- First link imports retained history (up to the existing 2,000/thread window); new events converge across active devices. Keep lightweight dedup IDs, deletion contexts, and explicit history retention floors beyond body pruning; an old snapshot must not resurrect pruned/unsent content. Pruning is local retention, distinct from explicit account-wide unsend.
- Replicate attachment metadata and `file_xfer_id`, not bytes or local paths. Render “File on Mac” until an explicit fetch from a device advertising a local copy succeeds. Availability claims expire and are not delivery receipts. Syncing history must never reexecute a file transfer, mirror delete, or auto-delete sender files.

## Removal, recovery, and key rotation

- On management device, “Remove lost phone” signs/persists the next roster revision, tombstones its membership serial, cancels enrollment sessions for it, closes its connections, and discards queued sends to it. Gossip the signed update to siblings and known friends; known-revoked endpoints cannot return through legacy hello, chat repair, or folder auto-friend paths.
- Every receiver persists its highest verified authority state and rejects rollback. Fetch missing chain segments before accepting a higher revision. A peer that has not learned the revocation may still accept the lost phone: serverless revocation is eventual, with no bounded global completion while peers are offline. Show which reachable devices acknowledged; do not claim remote wiping or universal logout.
- Transport sessions are pairwise QUIC: there is no shared account decryption key to rotate on ordinary device removal. Stop sharing future operations and blobs with the removed endpoint. It retains all previously learned contacts/chats/files. Freshly arriving operations from it are rejected under the current roster even through another sibling.
- Offer an offline recovery kit at creation: root seed encrypted by a high-entropy generated recovery secret, account genesis/chain, and roster checkpoint. Keep it outside ordinary device sync/diagnostics. Restoring management first fetches the latest public chain from surviving devices, then rotates authority before new administration; verify a recovery checkpoint or obtain peer state rather than resetting revision to zero.
- If the management Mac is lost, use that recovery kit on a surviving/new device, rotate the root signing key and revoke the lost Mac. Without management key or recovery kit, existing members can continue existing communication but cannot securely add/remove members. If all keys/copies are lost, create a new account and reverify with friends; there is no password-reset service.
- Root rotation publishes an old-root-signed successor key/generation and new-root-signed roster, chaining back to `R0` so `account_id` stays stable. Keep one active management writer; rotate during management transfer and erase the prior private root after successful installation. Reissue remaining device certificates under the new root and refresh the offline recovery kit before retiring the old key: an old kit cannot administer a newer root generation. Rotation material and retired-key rejection state persist with the chain.
- If a stolen management root can sign competing rotations, peers cannot globally decide the rightful branch. Freeze on detected forks; for suspected root compromise require friends to verify a fresh identity/fingerprint out of band rather than treating an old-root signature as sufficient recovery. Offline recovery and automatic continuity cannot both defeat a fully compromised authority.
- Rotating a normal endpoint key is replacement enrollment plus revocation of the old serial; account ID/contact stays stable for upgraded peers. Legacy peers and endpoint-bound folders require reintroduction/re-pairing. A device leaving voluntarily deletes its local account secrets/state but needs management's signed removal to revoke remote trust.

## Diagnostics boundary

- Read `telemetry.rs` and `diagnostics-worker/DIAGNOSTICS-SETUP.md` together: the setup doc/settings comments say empty URL disables uploads, but actual `endpoint_for` falls back to a built-in collector; `share_diagnostics` gates uploads. The implementation also sends a per-install `diag-id` and display name. Do not use that service/identifier as account discovery, recovery, or membership authority.
- Keep diagnostics consent, URL, logging level, `diag-id`, and watermarks local; linking must not copy another device's opt-in or correlate installs by account ID in telemetry. Export excludes root/recovery material, invitations/tokens, membership chains, account journal, contacts, and chat content.
- Add bounded reason codes/counts for link failures, signature rejection, stale roster/fork, sync lag/batch size, migration failure, and persistence failure. Never log raw tokens/codes, account/endpoint IDs, private keys, names, paths, or record bodies. Extend redaction/export tests to encoded codes and base32 account IDs; regex redaction is a backstop, not permission to log secrets.
